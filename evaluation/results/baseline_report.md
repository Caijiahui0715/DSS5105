# Baseline comparison: interpretation (2026-11-11)

The table of figures is `baseline_comparison.md` (generated by `compare_systems.py`). This page gives the interpretation and caveats.

## What was compared

| System | What it is | How it runs |
|---|---|---|
| B1 | Portal-style: only the filters a rental website offers (budget, whole unit or room, room type, district, bedrooms, bathrooms, area, property type, furnishing, distance to MRT), then rent from lowest to highest | No model; takes each turn's gold conditions directly |
| B2 | Weighted score: every condition is a hard filter, then a fixed weighted score (rent and MRT 1 share each, each priority the user states 2 shares) | No model; takes each turn's gold conditions directly |
| B3 | An LLM recommending directly: the main fields of all 369 listings go into the prompt as one table, with no tools | The same model as the agent (gpt-5.6-luna) |
| B4 | The earlier fixed workflow (`graph.py`): the nodes run in a fixed order and the model only understands the request and writes the reply | The same model and the same search and ranking code |
| B5 | The current agent (frozen at `1b6ba07`) | Holdout 3 runs; dev set 1 run (dev5) |

The baseline code was frozen after the dev-set runs (the hashes of `baselines.py`, `run_baselines.py` and `run_eval.py` are recorded at the top of each result file); the holdout was run only after that, and nothing was changed after seeing it.

## Holdout results (20 cases)

| What | B1 portal | B2 weighted | B3 LLM | B4 workflow | B5 agent |
|---|---|---|---|---|---|
| Hard-condition violations | 12% | 0% | 4% | 0% | 0% |
| Condition the data does not state, treated as met | 25% | 0% | 0% | 0% | 0% |
| Stated ranking followed | 3/7 | 1/7 | 3/7 | 7/7 | 21/21 |
| Category B: lists the listings needing confirmation | 0/2 | 0/2 | 1/2 | 1/2 | 5/6 |
| Category C: gives the right smallest relaxation | 0/2 | 0/2 | 1/2 | 1/2 | 6/6 |
| Conditions parsed (whole turn) | given gold conditions | given gold conditions | – | 14/17 | 47/51 |
| Numbers with no traceable source | 0/96 | 0/90 | 4/97 | 1/182 | 3/470 |

On the dev set, category B: B1, B2 and B3 are all 0/6, and B4 and B5 both 3/6; category C: B1 and B2 0/6, B3 4/6, B4 and B5 6/6.

The B and C rows are judged automatically from the reply text. I read every B4 and B5 case judged as not done, and each one really was not done. For example, in holdout case B08 run 3, B5 said "no listing has an unstated lease", when 37 do; in dev cases B01–B03 it gave only the confirmed listings and did not mention the ones with missing data. `compare_systems.py --detail` shows the result for every case.

## Main findings

1. **Portal-style filtering (B1) cannot express many needs.** Cooking, gender, landlord living in, air-conditioning, lease, commute and nearby food places have no matching portal filter and can only be ignored, so 12% of the listings shown clearly fail a condition and 25% are treated as meeting a condition the data does not state. This is even with every condition filled in correctly.

2. **Most of the weighted score's (B2) good results are given to it.** It shows "0% violations, 100% display correct" for three reasons: its conditions come straight from the gold answer; it judges fields with the same rules that generate the gold answer; and the complete conditions after changes across turns are also handed to it. These columns are almost bound to look good for it. On the items that really test it, it is the worst:
   - Where the user stated a ranking, it ranked only 1 of 7 holdout turns right (dev set 2/11). It adds the factors into one score instead of following the user's order.
   - It never lists listings that need confirmation (holdout 0/2, dev set 0/6). In B08, for example, 24 listings are confirmed and another 37 do not state a lease; it gives only the former, and the user never learns the others exist.
   - When nothing matches, it says only "No listings match" and suggests no relaxation (holdout 0/2, dev set 0/6).
   - It cannot ask first, say the data does not know, or decline.

   So B2 answers the question "if the user were understood perfectly, would filtering plus a weighted score be enough?" The answer: filtering is enough, ranking is not, and it does not handle missing data or requests with no match.

3. **The LLM without tools (B3) fabricates and miscalculates.**
   - Dev case C02: it placed a D12 listing in D03 and called it a full match.
   - Holdout case C08: it said the commute had to be relaxed to 56 minutes before anything matched; the right answer is 29 minutes.
   - In a trial run it turned "6-minute walk to MRT" into "6-minute commute to the faculty".
   - Where the user stated a ranking, it ranked only 3/7 right.
   - It reads the whole listing table every turn (about 29,000 tokens), which will not fit once there are many more listings.

   It does do some things well: in H01 it gave the original price (1,000) and the difference (100) correctly, because the table has an original-price column.

4. **The fixed workflow (B4) and the agent (B5) are close on search cases.** Both use the same search and ranking code; both have 0% violations, and both followed every stated ranking. Their parsing errors are also alike: in A12 both added "the advertiser prefers male tenants". They differ mainly in behaviour: asking first, declining and saying the data does not know (categories D, E, F and H), which is compared by human scoring.
   - One counter-example: on the original price in H01, B4 was right and B5 was wrong in all three runs, because the workflow's path for listing details returns the original price.

5. **Conclusion:** compared with portal filtering and the weighted score, the agent's advantage is that it can express more conditions, ranks strictly in the order the user states, marks listings with missing data separately, and gives the smallest change when nothing matches; compared with an LLM recommending directly, its advantage is that every number has a source and nothing is made up. Compared with the earlier workflow, the automatic metrics show no difference; the behaviour scores decide.

## Caveats (to state in the report)

- **B1 and B2 are given the gold conditions**, which does the "understanding the user" step for them, so their results are an upper bound. B5 has to understand the user itself (47/51), a difficulty the baselines do not face.
- **Each baseline ran once; B5 ran three times on the holdout.** Rates can be compared, but the baselines have no data on consistency across runs. B1 and B2 are deterministic, so running them again would give the same result.
- **For category C (no match), B3's violation count is too strict.** B3 has no notion of a preview, so it lists listings that match only after relaxing as recommendations. In C07, for example, its relaxation (budget up to 2,205) is right, but the listings it lists count as violations. C08 is a genuine wrong answer.
- **"Numbers with no traceable source" are candidates, not proven fabrications.** Of B3's 4 on the holdout, H01's 100 is correct; C08's 5,900 and 17 minutes are its example of relaxing both conditions and were not checked. B5's 3 were all checked and are all true.
- **We wrote B3's prompt.** It was written to be as fair as possible: it tells the model to mark listings needing confirmation, to give the smallest change when nothing matches, and to ask first when a request is vague. A different wording might give different results.
- **Categories D, E, F and H are not in the table** and are scored by people. B1 and B2 can only search and can do none of these. B3's and B4's replies are in `b3-*_review.md` and `b4-*_review.md` and can be scored the same way.
- **Cost**: B3 used about 1.48 million input tokens on the dev set and about 0.84 million on the holdout.
