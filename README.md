# DSS5105 — Singapore Rental Decision Agent

English | [中文](README.zh-CN.md)

A rental decision agent for NUS students looking for a home in Singapore. An LLM agent (LangGraph) understands requests in English or Chinese and calls deterministic tools that search a PostgreSQL database of PropertyGuru listings, check each listing's link, give commute times to the user's NUS faculty from OneMap routes, and rank, compare and cost the options; facts in its replies come only from those tools. The front end is the Streamlit app in `app/`, `server.py` (FastAPI) serves accounts, conversations and the agent, and a fixed LangGraph workflow (`graph.py`) is kept as an evaluation baseline.

## Getting started (for team members)

Follow these steps once to run it on your own computer. Run the commands in PowerShell from the repository root; on macOS, replace `.\.venv\Scripts\python.exe` with `.venv/bin/python`, `Copy-Item` with `cp`, and `\` in paths with `/`. Every setting, how to use the app and common problems are explained in the [user guide](USER_GUIDE.md).

1. **Install the tools** (once per computer)
   - [Git](https://git-scm.com/downloads).
   - [uv](https://docs.astral.sh/uv/getting-started/installation/): `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`, then reopen the terminal. uv downloads the project's Python 3.12 itself; there is nothing else to install.
   - [PostgreSQL](https://www.postgresql.org/download/windows/): use the installer, keep the default port 5432, and remember the password you give the `postgres` user; the Stack Builder at the end can be skipped. It then runs as a Windows service that starts with the computer.
2. **Get the code and the data**
   ```powershell
   git clone <repository URL>
   cd DSS5105
   ```
   Then ask the group for the whole `output-final-delivery` folder (the final data, not in Git) and put it in the repository root. The database import uses its `rental_data_v1.json`, `rental_data_v2.csv` and `removed_listings.csv`; the source evidence in listing details comes from `source_evidence_v1.json`.
3. **Install the dependencies**
   ```powershell
   uv sync                    # backend, into .venv
   uv sync --project app      # front end, into app/.venv
   ```
4. **Fill in `.env`**
   ```powershell
   Copy-Item .env.example .env
   Copy-Item app\.env.example app\.env
   ```
   The root `.env` needs at least these lines (one `KEY=value` per line; no comments after a value):
   ```
   OPENAI_API_KEY=your key
   OPENAI_MODEL=a model name that supports tool calling
   DB_HOST=localhost
   DB_PORT=5432
   DB_NAME=dss5105
   DB_USER=postgres
   DB_PASSWORD=the password set when installing PostgreSQL
   ```
   `DB_NAME` can be any name; the next step creates that database. `app/.env` needs no changes. Neither `.env` is committed to Git, and don't paste the key into group chats either.
5. **Prepare the database**
   ```powershell
   .\.venv\Scripts\python.exe .\setup_database.py
   ```
   It creates the database and tables, imports the listings and commute times, and ends by printing the number of usable listings ("Done: N usable listings, …"). It can be run again.
6. **Start**: open two terminals and start the backend first, then the front end.
   ```powershell
   .\.venv\Scripts\python.exe .\server.py                     # terminal 1: backend
   uv run --project app streamlit run app/streamlit_app.py    # terminal 2: front end
   ```
   Open http://localhost:8501, register an account (username of 3–20 letters, digits or underscores; password of at least 8 characters), choose your faculty and start chatting. Accounts are kept in your own database, so they are not shared between team members.

**Next time**: PostgreSQL is already running from startup, so only step 6 is needed (if startup says it cannot connect to PostgreSQL, the service has most likely stopped; see "PostgreSQL is not running" in the [user guide](USER_GUIDE.md)). After pulling new code, run `uv sync` and `uv sync --project app` first; when the group shares a new version of the data, replace `output-final-delivery` and run `setup_database.py` again. Restart the program concerned after changing a `.env`.

**Team members who ran an older version**: the backend now uses only PostgreSQL. Remove `AGENT_DB` from `.env`, add the `DB_*` settings and run `setup_database.py` once. The old `sessions.sqlite` is no longer used and accounts have to be registered again (the demo account too; `app/.env` needs no changes); delete the file once you are sure you don't need it.

If startup fails, read the message in the terminal first: the backend says what to check, and common cases are under "Common problems" in the [user guide](USER_GUIDE.md).

Deploying to AWS (the online site for the teaching team and the group): see [deploy/README.md](deploy/README.md).

## Multi-user web version

`server.py` is a local FastAPI service that serves both the API and a single web page, `static/index.html`; several people can use it at once.

- Accounts: open registration (when `REGISTRATION_CODE` is set in `.env`, registering needs that invite code, as on the online site); usernames are 3–20 letters, digits or underscores (case-insensitive), passwords at least 8 characters; only a salted scrypt hash of each password is stored. Five wrong passwords in a row lock the account for a minute. After signing in, the server issues a token in an HttpOnly cookie (valid for 7 days; the database stores only its SHA-256), and signing out revokes it.
- Conversations: each user can have several conversations, ordered by latest activity, and the latest opens by default; the title is the first 20 characters of the first message. A new conversation does not carry over earlier messages; while long-term memory is on, it starts from the long-term profile's criteria (see `profiles.py` under "Architecture"). Favorites and exclusions belong to the account and are shared by all its conversations. Each conversation's state is kept per thread by the LangGraph checkpointer, and the `threads` table records whose it is; opening someone else's conversation always answers "conversation not found".
- While a turn runs: the reply still appears in one piece, once the whole turn has finished and passed the fact check. While waiting, the page shows "Thinking…" with the current step in small print below (searching listings, checking listing links (listing 2), and so on), pushed with Server-Sent Events; tool arguments and model reasoning are not shown. A new message in a conversation whose previous message is still being processed waits its turn. Closing the page does not stop a turn in progress; the result is there after a refresh. When a turn fails (for example, the model call fails), the backend leaves a reply in the conversation saying that an error occurred, there is no reply and the message should be sent again, with the error type (such as `RateLimitError`) in its processing steps, so the page does not keep showing the turn as in progress; when the database cannot be reached this reply cannot be written, and the page asks for the message to be sent again after waiting 5 minutes.
- Processing steps: each reply can be expanded to list, in order, the tools called in that turn, link checks, currency conversions, replies rejected and rewritten, and so on; these steps are saved with the reply, so they are still there after a refresh or the next day.
- My faculty: chosen at registration (or left for later) and changeable at any time under "My faculty" in the left sidebar. Commute times are all computed to this faculty, in every conversation, and a change applies from the next message. It can be changed in chat too: when none is set, the agent first asks which faculty you are in and saves your answer; when one is set and you name another, the agent first confirms ("change your faculty to X? All conversations will then compute commute times to X") and changes it only after you agree, with the change shown at the start of the reply. A hypothetical such as "what if I were in the Faculty of Law" is only looked up, not saved.
- Deleting: a single conversation can be deleted (in the Streamlit conversation sidebar, with the bin on the open conversation's row, after confirming; not while a reply is being generated). "Delete all my data" (at the bottom of the Profile page, clickable after ticking a confirmation) deletes all of the user's conversations, long-term profile, favorites, exclusions and faculty setting, keeps the account and signs out every device. "Delete long-term profile" (on the Profile page, or saying "delete my long-term profile" in chat) deletes only the saved criteria and leaves the long-term memory switch as it is; saying "forget my information" in chat deletes the criteria and switches long-term memory off. Neither touches favorites, exclusions or the faculty.
- `--lan`: listens on 0.0.0.0 and prints the computer's LAN address (on the first run Windows shows a firewall prompt; allow private networks). This is plain HTTP: passwords and conversations are not encrypted on the local network, so use it only on a network you trust; by default it listens only on 127.0.0.1.

## Data and storage

- Everything is in the project's PostgreSQL. The connection settings are `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` and `DB_PASSWORD` in `.env`, shared with the data pipeline; `DB_CONNECT_TIMEOUT` is optional, 10 seconds by default.
  - `public` schema: listings (`listings`, `listing_enrichment`, `listing_metadata`, `district_lookup`) and commutes (`listing_commutes`, `nus_destinations`), written only by the data pipeline (`src/dss5105/data`, `build_commutes.py`).
  - `agent` schema: written only by the server. Accounts, tokens, the conversation list, long-term profiles, the long-term memory and auto-save switches (`user_profiles`), faculty settings, the accounts' favorites and exclusions (`user_listings`), a record of one-off data migrations (`migrations`), LangGraph's checkpoint tables, the link-check results `listing_health` (reused for 24 hours, also after a restart), routes to places users name, `place_routes` (see "Another commute destination"), and the `agent_listings` view.
  - The `agent_listings` view (`group_db.py`): every search reads it. It takes only listings with `scrape_status = 'active'`, computes the values used for ranking in the database (ranks of nearby food places and other amenities, area percentiles, the faster way to each faculty, routes to places the user named), turns V2 labels into the V1 wording that search uses, and joins district names, availability, review flags and link-check results. The server rebuilds the view each time it starts; after the data pipeline updates the data, the next query sees it without a restart.
  - First preparation (or after a new data version): run `setup_database.py`. In order, it creates the database (when the server does not have it yet), runs the table scripts in `src/dss5105/database/` that have not run yet, runs `load_data.py` (V1) and `sync_v2.py` (V2), writes `commute_faculty.csv` into the database, and finally builds `agent_listings` and prints the number of usable listings. It can be rerun, and the accounts and conversations in `agent` are not affected. It only adds or updates the listings in the files: old listings missing from a new V2 file and not listed in `removed_listings.csv` stay active, and the script says how many there are. It needs the data files in `output-final-delivery/` (shared within the group, not in Git). Faculties come from `faculties.py`; don't overwrite them with `seed_nus_destinations.py` any more.
  - Missing settings: when any of the five `DB_*` settings is empty, the server, `setup_database.py` and `build_commutes.py` stop at once and name it (".env is missing DB_USER. Add it and run again"), instead of connecting without it; tests that need the database are skipped with the same message.
  - Cannot connect: the server exits at startup and says what to check (whether the service is running, the connection settings, or run `setup_database.py` first). If the connection drops while running, that turn replies that the database cannot be reached right now and to try again later, and the next message reconnects automatically.
  - When re-importing listing data, clear only the tables in `public`; don't drop the whole database, or every account and conversation is lost.
- Tests: they use `<DB_NAME>_test` on the same server, created automatically on the first run (the database user needs permission to create databases; otherwise create it by hand in pgAdmin first). Each data set lives in its own schema: `mock` is the 12 fictitious listings in `tests/fixtures`, rebuilt before each test; `real` is the data in `output-final-delivery`, imported once per run with `load_data.py` and `sync_v2.py`; `storage` holds accounts and conversations, emptied before each test. When PostgreSQL cannot be reached, the tests that need the database are skipped with the reason, and the rest run as usual.

## Architecture

- `agent.py`: the outer agent. The model reads the conversation, the session state and the tool results, and decides itself which tools to call and how many times, with up to 5 rounds of tool calls per turn.
- The tools are deterministic code: `search_listings`, `explore_budgets`, `get_listing_details`, `explain_listing`, `compare_listings`, `shortlist`, `exclude_listings`, `estimate_costs` (and, with an account, `user_memory` and `faculty`).
- Comparison: `compare_listings` compares two or three listings at a time (with more, it asks the user to pick three) and builds a table in the order the user gave (monthly rent and how much more than the cheapest, commute to the faculty, MRT, rental and room type, area, bathrooms, furnishing, lease term, move-in, whether each meets the criteria as of then, and the link check, in both Chinese and English), with a one-line summary of the key differences worked out by the system. Listings whose link is no longer active or that are no longer in the data are not compared, which the system states at the start of the reply, and with only one left nothing is compared. The table is returned to the page with the reply, and the latest one is kept in the conversation state (`last_comparison`). The model only writes about differences, trade-offs and recommendations, without listing the data listing by listing again. The first time each account compares, the system says at the start of the reply that the table is in the "Compare" bar on the right (`user_profiles.compare_hint_shown`).
- `costs.py`: rental cost calculations (total rent, stamp duty, deposit, payment at signing, agent fee), with the rules at the top of the file; `estimate_costs` uses it.
- `decision.py`: three-state checks of each criterion (meets / does not meet / not stated in the data), the diagnosis that relaxes conditions one at a time, and ranking provenance. Strict-match results are exactly the same as those of `tools.search_listings`.
- `graph.py`: the fixed workflow, kept as the evaluation baseline (`demo.py --workflow`): the node order is fixed, and the model only interprets the request and rewrites a factual draft. These parts use the same code as the Agent:
  - Search split into "strict matches" and "needs confirmation" (`decision.search_with_unknowns`): with fewer than 3 strict matches, the rest are filled with listings to confirm, numbered on from them; with no strict match, it lists the conditions that block the results (`decision.diagnose_conditions`).
  - Commute to the user's faculty: the caller passes `faculty` in the input each turn (the faculty's English name, Chinese name or abbreviation all work), and the command line reads the faculty saved with the account; with no faculty but a commute condition, the end of the reply says so, as in the Agent.
  - The conversion of the number of occupants (`decision.occupant_rules`) and the fixed notes at the end of the reply.
  - "Why this listing / where does the price come from": the `explain_listing` intent (recognized without the model when the message contains a listing ID), answered as the Agent's `explain_listing` tool does.
  - The rules that map what the user says to criteria fields (`parser.FIELD_RULES`), used by both prompts.
  - Checking the numbers after the rewrite (`_reply_problems`): if the check fails, the factual draft is shown and the reason goes into `trace`, which `--trace` shows.
  - Only in the Agent, not in the workflow: another commute destination, budget exploration, cost estimates, long-term memory, and favorites and exclusions that belong to the account.
- `tools.py`, `response.py`: retrieval and URL checks, and the factual templates, shared by both flows. `mock_db.py`: the test database (see "Data and storage").
- `sessions.py`: the conversation tables in the `agent` schema and LangGraph's PostgresSaver (sharing one connection pool with the listings). The checkpointer saves each turn's full state per conversation (the criteria with the user's words for each, the messages, each reply's processing steps), and the `threads` table records which user each conversation belongs to; Agent and workflow conversations are stored separately.
- `accounts.py`: registration, password checks, sign-in lockout and tokens, using only the standard library.
- `group_db.py`: the connection pool for the project's PostgreSQL, the `agent_listings` view and the startup checks; `open_database()` connects and builds the view, and the web version, the command line and the commute scripts all use it.
- `setup_database.py`: prepares the database in one step (see "Data and storage").
- `src/dss5105/`: pizza's data layer; `database/` holds table creation and migrations, `data/` the V1 import, the V2 sync and the faculty table scripts. Recommendation logic is now all the agent's; the original `api/`, `backend/`, `commute/` and `decision/` are no longer used (planned to move into `archive/`).
- `faculties.py`: the address, coordinates and database faculty code (`code`) of each NUS faculty, used to locate location criteria by faculty name and as the destinations of commute times.
- `build_commutes.py`: computes offline, with OneMap, each listing's public transport time to each faculty (within 1.5 km it also compares walking) and writes `commute_faculty.csv`. The database is the source: it first exports `listing_commutes` to the CSV, computes what is missing, and writes back to the database when it ends (also when it stops on an error). The CSV is in Git, so a new database gets commute times by importing it with `setup_database.py`, without OneMap. `--import` / `--export` do only the writing or the export, for example `--import` after running `fix_transit_google.py`.
- `show_route.py`: prints the OneMap route from a listing to a faculty (each leg's mode, start and end, and minutes), to check doubtful commute times.
- `server.py`, `static/index.html`: the multi-user web version's API and page (the page is kept for development testing; the real front end is Streamlit, see "API for the front end").
- `profiles.py`: long-term profiles, the long-term memory and auto-save switches, and the account's favorites / exclusions (Agent only; the workflow baseline only reads the faculty saved with the account).
  - Long-term profile (`user_profiles.profile`): the criteria the user chose to save, each with its source (the user's words in a conversation and the date, or "changed on the Profile page" and the date); budgets are recorded as said (amount, currency, months covered). Conversation content is not saved, and the model cannot write to it freely.
  - It is updated only when the user saves or has chosen auto-save: changing the form on the Profile page, clicking "Save to long-term profile" in Home's "This conversation's criteria" (it lists the changes first and saves after confirmation), saying "save to my profile" in chat (tool `user_memory`, `action=save`), or with auto-save on (see below). Without auto-save, criteria changed in a conversation belong only to that conversation: the reply starts with "Updated this conversation's criteria: …", and above Home's criteria panel a note says how many changes are not saved to the long-term profile yet; the system does not ask in chat whether to save.
  - Only changed fields are merged: the conversation's current criteria are compared with the long-term profile it started from (or the values after the last save, kept as `profile_base` in the state), and only the fields that differ are written, cleared criteria included; other fields changed meanwhile in other conversations or on the Profile page stay as they are. For a conversation that did not start from the long-term profile, every criterion set in it counts. The Profile page's form also submits only the changed fields.
  - The long-term memory switch (`user_profiles.consent`): the criteria given at sign-up are saved straight to the long-term profile (with the source "given when you signed up"), long-term memory is switched on with them, and the first conversation starts from these criteria. Users who did not go through the sign-up form are "not yet on", and it switches on with their first save. It can be switched on the Profile page, or by saying "turn long-term memory on / off" in chat (`action=on` / `off`). Off is a pause: the saved criteria remain and can be viewed and deleted, but new conversations don't use them, the page is read-only and nothing can be saved; to save while it is off, the agent first asks whether to switch long-term memory on and save, and does so only after the user agrees (`switch_on=true`).
  - The auto-save switch (`user_profiles.auto_save`): while it is on and long-term memory is on too, criteria changed in a conversation (when `search_listings` is not a preview, or a new lease term is given in `estimate_costs`) are merged into the long-term profile at once, by the same rules as saving by hand (only changed fields), and the reply says the criteria were updated and saved to the long-term profile automatically. New users have "not chosen". While auto-save is off, long-term memory is not off and the offer has never been closed, once a Home conversation has criteria a bar above the chat input asks "Save the criteria you change in conversations to your long-term profile automatically? [Auto-save] ×": "Auto-save" switches it on (together with long-term memory, when that is not on yet) and at once saves the conversation's changes so far, and the bar turns into a sentence on how to switch it off, which goes when its × is clicked; after the offer's × is clicked, the offer never shows again (`user_profiles.offer_closed`). It can also be switched under "Long-term memory" on the Profile page (greyed out while long-term memory is off), or by saying "turn auto-save on / off" in chat (`action=auto_on` / `auto_off`). While long-term memory is off, the auto-save setting is kept but paused, and it resumes when long-term memory is on again; "forget my information" also switches auto-save off, and "Delete all my data" also clears the choice made on the offer.
  - New conversations: when the switch is on and there are saved criteria, `POST /api/conversations` applies them when it creates the conversation (budgets not in SGD or per year are converted again at the day's rate; when conversion fails, the last monthly rent limit is used and the reply says so), and writes an opening message from the system listing them ("Your long-term profile's criteria are set: …"); the front end shows this message and these criteria before the first message is sent. Saying "use my long-term profile" in chat applies it again (`action=restore`); "what is my long-term profile" is `action=show`.
  - Favorites and exclusions (`user_listings`): they belong to the account, are shared by all its conversations, take effect with one click and are not affected by the long-term memory switch. A listing is either a favorite or excluded, and the later action wins. Searches no longer recommend favorite or excluded listings; when a favorite fully meets this search's criteria, a fixed sentence at the end of the reply says so. The Profile page lists the excluded listings, which can be restored. Favorites and exclusions stored earlier in each conversation and in the long-term profile were merged into the account the first time the server started (the long-term profile first, then the conversations from the earliest last activity to the latest, a later one winning for the same listing), once only.
- When an earlier conversation continues, the Agent first removes from the shortlist, each turn, the listings no longer in the current data, with a fixed note; when the user comes back on a later day, it clears the old relaxation suggestions and the last search's counts (they rest on old data and old link checks), and reminds the user to update a move-in date that has passed.

## Streamlit front end (`app/`)

The real front end is the Streamlit app in `app/` (pages made by Fangyue). It is a separate uv project with its own environment, apart from the backend's; run the two in two terminals:

```powershell
.\.venv\Scripts\python.exe .\server.py                                   # terminal 1: backend, http://127.0.0.1:8000
uv run --project app streamlit run app/streamlit_app.py                  # terminal 2: front end, http://localhost:8501
uv run --project app pytest app/tests                                    # front-end tests (offline demo mode, no backend needed)
```

Accounts, listings, recommendations, commutes, conversations and favorites all come from the backend: chat goes to the real agent, and the front end neither scores listings itself nor uses demo commutes. The front end's settings are in `app/.env` (not committed): `BACKEND_URL` (default `http://127.0.0.1:8000`); with `DEMO_USERNAME` / `DEMO_PASSWORD` set to a demo account registered on the web first (for example `demo_user`), the sign-in page shows "Continue with demo account", and everyone shares that account's conversations; `AGENT_MODE=mock` switches to an offline demo that does not use the backend (static files and a scripted demo agent). The interface is in English by default and can be switched to Chinese on the sign-in page and in the conversation sidebar. The agent replies in the language of the message itself (Chinese for a Chinese message), and uses the interface language only when a message shows no language (just a number, a district code or "yes"). The interface follows the message's language too (a Chinese message switches it to Chinese, an English sentence back to English), so the listing cards and the map are in the same language as the reply; once the user has picked a language with the switch, that choice holds for the rest of the session. "Remember me" keeps the sign-in token in a browser cookie for 7 days (page scripts can read this cookie, unlike the web version's HttpOnly cookie); signing out deletes the cookie and revokes the token.

## API for the front end

Besides the endpoints the chat page uses, the following are for the Streamlit front end to call from its own server (conversation state is all on the server, and the front end passes only the conversation ID and what the user said; `app/adapters/backend_client.py` is the front end's side of these calls, and `tests/test_frontend_client.py` checks that the two sides agree):

- No sign-in needed: `GET /api/faculties` returns each faculty's `name`, `zh`, `campus`, `code`, `latitude` and `longitude` (for the sign-up form and the map); `GET /api/options` returns the districts that have listings, `{"code", "name"}`, and the property types, for the sign-up and profile forms, and whether sign-up needs an invite code (`invite_code_required`).
- Sign-in: `POST /api/token` (`{"username", "password"}`) returns `{"token", "token_type": "bearer", "username", "faculty"}`, and each later request carries `Authorization: Bearer <token>`. Sign-up still uses `POST /api/register` (it may include `faculty`, and `invite_code` when one is needed), `POST /api/logout` revokes the token, and `PUT /api/me/faculty` changes the faculty. The web page's cookie sign-in is unchanged. All the endpoints below need sign-in.
- Listings: `GET /api/listings?limit=50&offset=0` (`limit` at most 200) returns `{"total", "listings"}`, with the same fields the agent ranks with (including `commutes` to each faculty, `live_status` from the link check, `lease_term` as advertised and `photos` links; `rent_monthly_sgd` is the rechecked monthly rent, and the originally advertised one is in `rent_monthly_sgd_card`). `GET /api/listings/{id}` returns `{"listing", "source_evidence"}`, the latter being the listing page's full record (images, original text, field evidence), or `null` when there is none; an unknown listing returns 404.
- Conversations: `POST /api/conversations` creates one (it may include `{"language": "zh" | "en"}`, the language of the opening message; while long-term memory is on, the conversation starts from the long-term profile's criteria, see above). `POST /api/conversations/{id}/messages` (`{"message", "language"}`, where `language` is the interface language, `zh` / `en`, used only when the message itself shows no language, for example just `1000`; otherwise the reply follows the message's language) returns `progress` events (text in both `{"zh", "en"}`) and the final `reply` with Server-Sent Events. The `reply` has `text`, `steps`, the saved criteria `preferences`, each criterion's source `sources` (`{"quote", "date"}`), `items` for the page to list the criteria (each with `field`, `label` and `value` in `zh` / `en`, and `source`), the changes not yet saved to the long-term profile `profile_changes` (in the same format as `changes` below), the account's favorites `shortlist`, this turn's comparison table `comparison` (`null` when nothing was compared; the format is in `app/API_CONTRACT.md`), and `recommendations`: the listings this turn's search shows, `{"preview", "listings": [...]}`, each with `status` (`match` for a full match, or `needs_confirmation`, which comes with `unknown_conditions` and `unknown_condition_labels` written in the reply's language), `position`, monthly rent, MRT, `commute_minutes_to_faculty` and `commute_mode` to "my faculty", `lease_term`, `link_status` / `link_note` and more; it is `null` when the turn had no search, and the front end keeps the previous list. `preview` true means the search was only hypothetical and the criteria were not saved.
- Reopening a conversation: `GET /api/conversations` lists the conversations, `GET /api/conversations/{id}/messages` gives the messages and each reply's processing steps, and `GET /api/conversations/{id}` returns `{"id", "preferences", "sources", "items", "profile_changes", "recommendations", "comparison", "shortlist"}` (`recommendations` are the listings the latest search showed, and `comparison` the latest comparison table, in the formats above).
- Favorites and exclusions: these are the agent's shortlist and exclusion list; they belong to the account, are shared by all its conversations and are visible to the agent. `GET /api/me/listings` returns `{"shortlist", "excluded"}`; `POST /api/me/shortlist` (`{"listing_id"}`) adds a favorite (and un-excludes it if it was excluded), `DELETE /api/me/shortlist/{listing_id}` removes a favorite, and `DELETE /api/me/excluded/{listing_id}` restores an excluded listing; all of them return the same `{"shortlist", "excluded"}`.
- Long-term profile: `GET /api/me/profile` returns `{"memory", "auto_save", "auto_save_offer", "saved_on", "preferences", "sources", "budget", "items", "opening"}`: `memory` is the switch, `on` / `off` / `undecided`; `auto_save` is the auto-save switch (paused while long-term memory is off); `auto_save_offer` says whether Home should show the auto-save offer; `opening` is a new conversation's opening message as `{"zh", "en"}`, `null` when the switch is not on or there are no criteria. `PUT /api/me/profile` (`{"changes": {criterion: new value or null}}`, with criterion names as in `preferences`) changes the long-term profile, writing only the fields given, with the Profile page as their source; it returns 409 while the switch is off, and saving while it is not yet on switches it on. `PUT /api/me/memory` (`{"on": true/false}`) switches long-term memory, `PUT /api/me/auto-save` (`{"on": true/false}`) switches auto-save (switching it on also switches long-term memory on when that is not on yet), `DELETE /api/me/auto-save/offer` closes the offer (it never shows again), and `DELETE /api/me/profile` deletes the saved criteria; all of them return the same long-term profile.
- Saving a conversation's criteria to the long-term profile: `GET /api/conversations/{id}/profile` returns `{"memory", "changes"}`, where `changes` is how saving would change the long-term profile (each row with `field`, and `label`, `before` and `after` in `zh` / `en`); `POST /api/conversations/{id}/profile` (`{"switch_on": false}`) saves and returns `{"changes", "profile"}`. While the switch is off, it must carry `"switch_on": true` (after the user agrees to switch it on), or it returns 409. `POST /api/conversations/{id}/auto-save` is the offer's "Auto-save": it switches auto-save on and at once saves the conversation's changes so far, returning `{"changes", "profile"}`; it returns 409 while long-term memory is off.
- Deleting all data: `DELETE /api/me/data`, see "Deleting" above.

## The agent's boundaries

- Facts come only from tool results or the session state. Listing IDs, amounts, minutes and counts in a reply must appear in this turn's tool output, otherwise the reply falls back to the template draft; offering actions beyond its abilities, such as contacting landlords, confirming availability or booking viewings, also makes it fall back.
- When criteria change, the tool arguments must quote the user's words from this turn (`user_quote`); `preview=true` only looks, without changing anything. `set` holds only the fields to change to a new value, and empty and default values are ignored (the model sometimes passes every field, which would otherwise clear saved criteria); to remove a saved criterion, list its field name in `clear`. Changes to criteria, favorites and exclusions are shown to the user in fixed wording.
- Not stated in the data no longer counts as not meeting a condition: listings that meet every other condition but leave some requirements unstated are listed separately as "needs confirmation", with the condition that held them back.
- When a saved search has no strict match, relaxation suggestions following the original workflow's one-condition-at-a-time rules (budget about +10%, MRT +5 minutes, and, with a lease term set, also trying 1-year and 2-year leases, with the results link-checked) are added in fixed wording at the end of the reply; with commute limits set, each destination is also tried 10 minutes looser. When no suggestion is found but listings that need confirmation are already listed, the sentence saying nothing was found after relaxing is left out (what holds them back is data that is not stated, which relaxing other conditions does not change).
- Whole unit or room uses `rental_scope` (entire_unit / room), from the V2 data's rental type; listings that don't state it are "needs confirmation" and are not taken as whole units. When asking for more criteria, the agent first asks whole unit or room, and asks about the room type only once room is chosen. When the user has not chosen and the full matches include both, the end of the reply says in fixed wording which kind is shown, with the other kind's count and lowest monthly rent.
- Ranking: MRT walking distance always counts (metres ÷ a reference distance, which is the walking limit × 85 m, or 850 m without a limit), plus monthly rent ÷ budget when there is a budget; convenient food and the commute to NUS count only when the user asks for them. `ranking_priority` keeps up to 3 preferences: the named ones share 70% equally and the other factors share 30% equally, but no other factor outweighs any named one (with 3 named and 1 other, for example, each of the four gets 25%); with none named, all count equally. Over several turns, "also / too / as well" adds a preference and "never mind / change to / only" replaces them; when it is unclear, it adds, and shows the change in fixed wording so the user can correct it directly. With more than 3, it first asks the user which three matter most. Every named factor needs data, and listings missing any of them are "needs confirmation". Listings without MRT data, or whose nearest station is not open yet, count at the reference distance (a ratio of 1); but when the user names MRT as a priority, such listings are "needs confirmation". Ties are broken by the highest-weighted factor first, then the next, and by monthly rent last.
- Number of occupants (`occupant_count`): the system cannot find several rooms in the same unit, so it assumes one room per person. With 2 or more, code (`decision.occupant_rules`, not the model) saves the rental type as whole unit and the minimum bedrooms as the number of people (leaving a larger saved bedroom count as it is, and using the user's own bedroom count when given in the same sentence), and the end of the reply says in fixed wording that it searched whole units with at least N bedrooms, one per person, asking the user to give the total number of bedrooms needed if some will share a room; when room was chosen before, it explains why it switched to whole units. The one exception is 2 people who chose room: it searches for the two sharing one room, and says at the end that they can switch to 2-bedroom whole units to have a room each. A bedroom count exactly equal to the previous number of people counts as set from the number of people: when the number changes to 2 or more, it follows; when it changes to 1, or the search no longer goes by the number of people, it is removed too, whole unit is kept, and the end of the reply asks whether to look at single rooms as well. The model sets only `occupant_count`; the prompt tells it not to set bedrooms, whole unit or a "more space" ranking preference itself. The workflow baseline uses the same code.
- Judging the number of occupants: a whole unit for up to 6 people meets the condition (the legal limit for private homes and HDB flats of 3 rooms or more, by URA / HDB rules), and more than 6 is "needs confirmation". A room for 1 person meets it; for 2 or more, a listing advertised as 1 pax does not meet it, and one advertised as 2 pax or more, or not stating it, is "needs confirmation", with a note that the advert says N pax and how many people can stay is for the landlord to confirm. The "N pax" in the data is only a label on the PropertyGuru card, and sometimes counts the whole unit (the field description says its scope is unconfirmed), so it is not taken as how many people a room can take; whole-unit listings never have this label.
- Bold in replies: before saving and sending a reply, the backend moves punctuation at either end of bold text outside the `**` (`**主要取舍：**第1套` becomes `**主要取舍**：第1套`); otherwise Markdown would show the asterisks as they are.
- Restrictions (three states: meets / does not meet / not stated, where not stated is always "needs confirmation", whole units included): `tenant_gender` (the gender of the occupants as the user states it: female / male / mixed, checked against the data's gender_restriction), `landlord_not_living_in` (no live-in landlord), `furnished_required` and `air_conditioning_required`.
- Commute time: `max_commute_minutes` and the ranking preference `commute` mean the time from the listing to "my faculty", the faculty saved with the user's account: by public transport leaving at 8:30 on a weekday morning (OneMap routes, walking legs included); when the faculty is within 1.5 km in a straight line, the OneMap walking route is checked too and the faster one is taken, and replies say "about X min walk" or "about X min by public transport (leaving 8:30 on a weekday)". The data comes from the database's `listing_commutes`, generated by `build_commutes.py` and also saved as `commute_faculty.csv` (columns listing_id, faculty, minutes, mode, departure; mode is transit, walk or transit_google (see two items below), and empty minutes mean there is no usable route). This file, in the project root, is the only CSV committed to Git (`.gitignore` ignores the other CSVs and lets it through with `!commute_faculty.csv`); after pulling, team members run `build_commutes.py --import` (or `setup_database.py`) to write it into their own database, without a OneMap account. One person reruns the script and commits the result, so that several people don't each recompute and conflict when committing; after a new version of the listing data, it must be rerun for new listings to get commute times, and listings without a commute record show as having no data. A rerun fills only what is missing: new listings, walking checks the old file lacks, and routes not computed after an earlier interruption; when OneMap times out three times in a row, the script stops, keeping everything already computed, and the next run continues, without recording timeouts as "no route". When a listing has no commute data or the user has not set a faculty, the commute always counts as "not stated": listings with a commute condition are "needs confirmation", and with no faculty set, a fixed note at the end of the reply points to setting one. When the user asks how long the trip to school takes and there is no data, the agent says so plainly and gives the straight-line distance to the faculty and the walk to the nearest MRT as a reference, without estimating minutes. For places other than the faculty, see the next item, "Another commute destination". Tests use mock minutes from the fixtures.
- Another commute destination: besides the account's faculty, a conversation's criteria can have one more destination, `other_destination` (`query` is a faculty's English name or an English place name / address / postcode, `name` is what it is to the user, such as "roommate's faculty" or "gym"; the system locates it and adds `faculty` and coordinates), with the limit `max_other_commute_minutes` (an extra condition; without data, "needs confirmation").
  - Faculties use the times already in `listing_commutes`; other places are computed live with OneMap by `place_routes.py` the first time they are used (leaving 8:30 on a weekday, and comparing walking within 1.5 km, as `build_commutes.py` does) and stored in `agent.place_routes` (keyed by `place_key`, the coordinates to about 1 m; minutes are empty when there is no route), and the view's `place_commutes` column gives each listing's time by place.
  - Only listings that might be shown are computed (`decision.route_candidates`: those meeting every condition the data always states, with the budget 10% looser, and with coordinates). With more than 120, the tool stops first and the model asks the user, in fixed wording, whether to wait; once the user agrees, it searches again with `wait_for_routes=true`. Six requests run at once, under one rate limit for the whole backend (`ONEMAP_CALLS_PER_MINUTE`, 240 per minute by default); when OneMap answers HTTP 429, all requests pause 10 seconds and retry. Failed routes are not saved and are tried again at the next search, and the end of the reply says in fixed wording how many could not be computed for now.
  - With two destinations, the ranking preference `commute` takes the larger of the two legs, each divided by its limit (45 minutes when no limit is given), that is, it ranks by the longer leg; both legs need data. With no faculty set and only the other destination, only that leg counts, and there is no prompt to set a faculty.
  - Only one is allowed: when there is one and the user names a new place, the tool does not save it, and the model reminds the user in fixed wording that besides their faculty only one more destination can be added and asks whether to replace it; once the user agrees, it searches again with `replace_destination=true`. With a new place, the old limit goes too (a new limit given at the same time is used). Removing the destination removes its limit too. A destination that is the user's own faculty is not saved.
  - Like the other criteria, it can be saved to the long-term profile and is carried into new conversations; listing cards, replies, details, ranking explanations and the comparison table all show both times. The scripts need `ONEMAP_EMAIL` / `ONEMAP_PASSWORD` in `.env`.
- When OneMap's results were checked on 2026-10-07, two listings at 49 Normanton Park (24611200, 24666342) took 81–110 minutes by public transport to faculties 1.5–4.6 km away, while other listings at the same distance took 25–37 minutes, so their times to the 16 faculties use Google Routes API public transport routes instead (`fix_transit_google.py`, leaving 8:30 on a weekday, mode `transit_google`). Replies still say "about X min by public transport (leaving 8:30 on a weekday)", and ranking explanations name Google public transport routes as the source. `UNRELIABLE_TRANSIT` in `build_commutes.py` lists these two listings, so reruns neither ask OneMap about them nor overwrite these rows; recomputing them needs `GOOGLE_MAPS_API_KEY` in `.env`. Listings at Sentosa Cove are generally 45–50 minutes slower than their distance suggests, and two have no public transport route; public transport there seems to be genuinely poor, so they are kept for now.
- Area: an explicit minimum area uses `min_area_sqm` (square metres; sqft × 0.09290304) as a filter; "a bit more space / spacious" adds `space` to `ranking_priority`, without needing a budget or rental type first. The space preference gets its weight by the rules above and ranks by area percentile within the same rental type and area scope, never comparing a room's square metres with a whole unit's directly. Whole units use `floor_reported` and rooms `room_reported`; listings with the area not stated, the rental type unknown, or a room reporting only the whole unit's area are "needs confirmation". Search results and details show the area scope.
- The other rental requirements in the data are supported too (missing data still means "needs confirmation"): bathrooms `min_bathrooms`, private bathroom `private_bathroom_required`, pets `pets_allowed_required`, price type `rent_price_types`, project / address / street / postcode `title_keyword` / `address_keyword` / `street_name` / `postcode`, nearest operating MRT station `mrt_station`, number of nearby stations `min_mrt_stations`, maximum walking metres `max_mrt_distance_m`, earliest listing date `listed_after`, and the landlord's explicit gender preference `gender_preference`.
- Furnishing uses `furnishing_types` (fully furnished / partially furnished / unfurnished / furnished with the level not stated), and how much cooking uses `cooking_level` (light accepts light cooking or no restriction; full accepts only no restriction; none requires no cooking). The old `furnished_required` and `cooking_required` still work; changing to unfurnished or no cooking must clear the conflicting old condition, otherwise the tool returns an error and saves nothing.
- Minimum counts nearby: `min_food_places`, `min_hawker_centres`, `min_libraries`, `min_sports_facilities`, `min_healthcare_places`, `min_community_centres` and `min_schools`. The first six count places within 1 km in a straight line; schools and MRT use PropertyGuru's nearby counts; healthcare counts mix hospitals and pharmacies, so they cannot promise a hospital nearby. When the user only wants "more", the ranking preferences `food_places` / `hawker` / `libraries` / `sports` / `healthcare` / `community` / `schools` are used, without inventing a count threshold.
- The walking limit to the nearest school uses `max_school_walk_m` / `max_school_walk_minutes`, and "near a school" uses the ranking preference `school_distance`. These mean the nearest school in the advert, not NUS or any particular school. `pg_mrt_nearest_walk_m` is a fallback source for the MRT distance in metres but still excludes stations not yet open; the total number of MRT stations nearby does not mean that all of them are operating.
- Location range uses `nearby_location` (`query`, or `latitude` / `longitude` the user gives, and an explicit `radius_m`). Place names are resolved with the existing OneMap setup, except NUS faculties (see the next item); when several places match or the API fails, the location condition is not saved and the agent asks for a more specific address / postcode / coordinates. Distances from coordinates are straight lines, and the listing's `coord_error_m` decides at the edge: when the error crosses the range limit, the listing is "needs confirmation". Location and the newer conditions support saving, clearing and previewing without changing the saved criteria, with rules shared by the Agent and the workflow.
- NUS faculty addresses: `faculties.py` records the 16 faculties / schools in `facultyaddress.docx` (name, main building, address, campus), with coordinates from OneMap lookups of the addresses on 2026-10-06 (where one postcode has several buildings, the one the document names). When the user names a faculty in English, in Chinese or by abbreviation (such as School of Computing, 商学院 or SoC), the recorded coordinates are used directly, without calling OneMap, so it is never judged ambiguous because one postcode has several buildings. The user still needs to say how far from the faculty. Each faculty is a separate commute destination, so the Lee Kuan Yew School of Public Policy at Bukit Timah and Duke-NUS at Outram have their own commute times too. To change an address or add a faculty, edit `faculties.py` (the coordinates need a new OneMap lookup) and rerun `build_commutes.py`; when an existing faculty's address changes, first delete that faculty's rows from `commute_faculty.csv`, or they are taken as already computed and skipped.
- Listing photos: the 2026-10-23 V2 data added a `photos` column (up to 6 PropertyGuru image links per listing, as a JSON list, all on sg1-cdn.pgimgs.com). `migration_photos.sql` adds `photos TEXT[]` to `listings`, `sync_v2.py` writes the list into it (empty when an older file lacks the column), the `agent_listings` view carries `photos` (an empty list when there are none), and the listings API returns them as they are. The web cards use `photos` first, and the images in `source_evidence_v1.json` otherwise; photos of the home itself come before those of the development, and agents' headshots and site icons are not shown. Cards and the Home panel show only the first photo: the Streamlit server downloads it (2-second timeout, cached for an hour, with a placeholder when it cannot load), with "Photo from the original PropertyGuru listing" below it, linking to the original listing; on Favorites, "All details", folded at the bottom of each card, shows all the photos as a row of thumbnails, which the browser loads straight from the links. Images are only linked, never stored; the photos belong to PropertyGuru and the agents who posted them, and permission is needed before publishing them.
- Lease term: the 2026-10-09 V2 data added `lease_term` ("1 year", "2 years", "Flexible", "Short Term", "Prefer not to say" or empty; about a third don't state it), taken as the shortest lease the landlord accepts. When the user says something like "only 6 months", "a year" or "signing for two years", it is saved as `lease_months` (in months, with the user's words recorded as for other criteria, and saved to the long-term profile with them). The filter rules: 1 year needs at least 12 months and 2 years at least 24, and wanting a longer lease also meets them; Flexible always meets it; Short Term meets it only below 12 months and is "needs confirmation" from 12 months up; not stated is "needs confirmation". When the lease the user wants is shorter than 6 months, the reply starts with a fixed note on the legal minimum lease (3 months for private homes, 6 months for HDB flats and rooms in HDB flats, by URA / HDB rules). The lease term is shown with each listing, in its details and on its web card.
- Costs: `estimate_costs` works out the costs for one or several listings (up to 3, or the shortlist), a monthly rent the user gives (in any currency) or the saved budget: the total rent over the lease, stamp duty (for leases of up to 4 years, total rent × 0.4%, rounded down, at least S$1; none when the average annual rent is under S$1,000), the deposit (1 month per year of lease), the payment at signing (deposit + first month's rent + stamp duty + agent fee) and the total cost excluding the deposit, noting that the good-faith deposit becomes part of the deposit after signing and is not counted again. The lease used is the one the user gave, else the listing's requirement (when that is longer than the user's, the listing's, as the reply states), else 12 months. An agent fee is counted only when the user says they use an agent, by default half a month's rent per year of lease plus 9% GST (the custom, and negotiable). The breakdown is shown in fixed wording, with the assumptions on the first line and a last sentence asking the user to give the lease, deposit or agent to recompute; the number of deposit months, whether an agent is used and the agent fee the user gave carry over within the conversation, and a lease term they give is saved as a search criterion. The sources of the rules are at the top of `costs.py` (checked on 2026-10-10).
- Property types use `property_types`: "condo / apartment" (公寓) means condominium, executive_condominium, apartment and walk_up_apartment, and "HDB" (组屋) means hdb_flat. When they are saved, the types actually used are shown, so the user can correct them directly.
- When the user is willing to raise the budget, or asks whether there is anything better, without giving a number, the agent calls `explore_budgets` to compare several price levels (database only: no link checks, nothing saved), explains whether the budget is the bottleneck, and asks which way the user wants to go.
- Budget: what is saved is a monthly rent limit. When the user gives a budget for a year, per year or for the whole lease, the Agent's `budget.months` (`budget_months` in the workflow) is 12 or the lease in months; the currency is converted first and then divided by the months, SGD annual budgets included, and the fixed conversion text at the start of the reply shows the calculation. When a monthly limit the Agent newly saves is above the monthly rent of 90% of the listings in the data, a fixed reminder asks the user to confirm whether it was meant as an annual or total budget. Conversely, when the converted monthly limit is under a tenth of the cheapest listing's monthly rent (for example "30 rmb a year", most likely missing a "万" (ten thousand) or "千" (thousand)), the budget is neither used nor saved: the reply starts with a fixed note asking for the right amount, and the other criteria are saved and searched as usual. A budget that is only somewhat low is searched as usual, with relaxation suggestions when nothing is found.
- When a tool fails, its error says what was wrong and what to do next (for example, call again with an ISO 4217 currency code, or ask the user); the prompt tells the model to correct the arguments and retry when it can, before answering the user. The currency alias RMB is turned into CNY before conversion.
- When a reply fails the checks, the reasons are sent back to the model for one retry; only if it fails again does the reply fall back to the template, or, when there is no template, to the saved criteria and the listings shown. `--trace` shows why a reply was rejected.
- Link checks follow the workflow's rules: in search, details, comparison and when viewing the shortlist, the original URL of each listing to be shown is checked (active / inactive / unknown; this does not change the ranking, inactive listings are excluded, and the reason goes into `listing_health.error_reason`); `explore_budgets` only counts in the database, without link checks. The model gets each listing's `link_note` (the same explanatory sentence as in the workflow) and `availability_note` and must state them separately; for listings whose link cannot be confirmed, the system lists the reasons in fixed wording at the end of the reply.
